## 桌面端启动速度：先测后优化

加了 `app/desktop/startup.go`（`GOSPEAK_STARTUP_DEBUG=1` 打印时间线，`GOSPEAK_STARTUP_EXIT_MS=N`
无人值守测量，`startupProbeFrontend` 轮询 `#app` 子节点并回报页面内 `performance.now()`）。

实测（本机 macOS/arm64，中位）：服务绑定+深链 ~13ms → mygo/Cocoa 到 WhenReady ~125ms →
代理+缓存预热 ~8ms → NewWindow ~110–170ms → WebView 内容进程 + 首个请求 ~215–440ms →
首个请求到 React 挂载 ~225ms ⇒ **合计 ~0.7–1.0s（中位 ~0.8s）**。

用实验否定掉的三个方向（不要再试）：
1. 隐藏窗口先加载再显示：首字节 888ms vs 显示中 899ms，无差异（~500ms 是 WebKit 内容进程启动）。
2. 麦克风权限推迟到首帧后：挂载 239ms → 238ms，无变化（getUserMedia 异步不阻塞）。
3. 推迟 Dock 图标/托盘：它们在 ~300ms 就做完，首屏在 ~800ms，本来不在关键路径。

真正的启动开销只有两处是我们的：① 启动即建覆盖层窗口（实测改回 eager 会让 overlay init
从 ~170ms 推迟到 300–580ms，故上一轮改成按需创建是对的）；② 首屏 JS boot ~225ms。

本轮改动：`mygo.config.ts` buildCommand 末尾用 `gzip -9 -k` 生成 `.gz` 边车；`proxyserver.go`
的 assetCache 优先读边车（缺失才运行时压缩），warm 从 ~50ms 降到 ~7ms，`.gz` 路径不允许直接访问。
`app/desktop/README.md` 补了「启动耗时」表 + 已否定方向清单。

### 复核校正（用户质疑「JetStream 不是持久化的么」后逐行核实）

A2 结论**方向成立但初版措辞过头，已修正报告**（含执行摘要 + P0 表 + A2 正文）：
- **对的部分**：签名密钥/黑名单确实写进 JetStream KV（`auth_store.go` 用 `kv.Create/Put`），JetStream 有磁盘持久化，不是纯内存。
- **真正的问题**：`bus/embedded.go:27,44` 把 JetStream `StoreDir` 设为 `os.MkdirTemp("", "gospeak-nats-js-*")`——每次启动都是**新的随机临时目录**，`:78-80` 优雅退出还 `RemoveAll`；`deploy/docker-compose.yml:49-52` 的 volume 只挂 db/logs/uploads，未覆盖；`config.go:84-88` 无 StoreDir / 外部 NATS URL 字段（底层 `OpenAuthStore(cfg.URL)` 支持 URL，但生产装配 `gin.go:309-312` 恒传内嵌 `NC`，URL 分支走不到）。⇒ 落盘了，但盘的生命周期 = 单次进程；下次启动换新目录、不读旧目录，即便容器没重建、旧 /tmp 残留也一样。
- **校正 1（panic）**：初版称"生产回退 staticKey 会 panic"过重。panic 仅当 backend 为空或 KV 全挂 **且** JWT_KEY 未配/仍是 default-secret 才触发（`jwt_key.go:149-156`）；正常部署 `init.sh:241` 生成随机 JWT_KEY + backend 正常，重启走 `randomKey()` 生成新 key → 旧 token 全量验签失败、全员重登，**不 panic**。
- **校正 2（黑名单影响面）**：改密/改角色/封禁的 token 失效靠 DB 里的 `user.TokenVersion`（`auth_service.go:464-469`、`middleware/auth.go:131-136`），不依赖 KV，重启仍有效；只有 **logout 吊销的 jti + refresh-family 重放保护**（`auth_service.go:316,321,452-460`）随 KV 清空，token 过期前"复活"。故实际面窄于"全部吊销失效"。
- **校正 3（开发/生产差异）**：`jwt_key.go:37-45` 开发模式用 static JWT_KEY，embedded NATS 重启**不换 key、不掉线**；只有生产模式受重启影响。
- **新增洞察**：生产 + backend 正常时签名用 KV 里的随机 `jwt.active`，`JWT_KEY` 只在回退分支被读——`init.sh` 生成、文档反复强调"生产必改"的 JWT_KEY 在正常生产路径里**并不参与签名**，真正的 key 由首个启动进程随机生成、随重启更换，运维不可见不可控。另 `NATS_WAL_PATH`（`config.go:88`）是事件断线重放 JSONL WAL（`bus/wal.go`），**不是** JetStream StoreDir。

## 前端路由页面保活（keep-alive）

`app/web/src/components/common/keepAliveOutlet.tsx` + `(app)/route.tsx` 的 `<Outlet />` 换掉。

**为什么不能直接缓存 Outlet**：TanStack Router 的 `Match` 只接受 routeId，渲染时从**当前** match store 取数据（`Match.js`/`useMatch.js` 已逐行确认）；切走后旧 match 不在链上，`matchContext` 也没从 index 导出。公开 API 无法同时渲染多个 location 的页面树。React 的 `Activity` 同样救不了——它靠 `display:none` 隐藏，隐藏页会被重新渲染而不是冻结。

**做法**：把 `/discover`、`/chat`、`/profile` 从「路由挂载」改成「常驻挂载」，路由退化为开关（和已有 `DomainWorkspace` 同一思路）。

- 隐藏用 `absolute inset-0` + `visibility:hidden` + `inert`，**不用** `display:none`：后者让滚动容器高度归零，浏览器把 scrollTop 清零，恰好毁掉最该保留的东西。绝对定位让每页独立占满、各自滚动，DOM 与滚动位置都不动。
- 页面 `lazy()` 动态导入 + 每页独立 `Suspense`。静态 import 会把 chat 的 128 kB 挂到 route chunk 上（实测 `route` 197 kB 时代 chat 128 kB），改 lazy 后 chat 只剩 5.86 kB 动态 chunk。
- 渲染期 `setMounted` 补挂，避免切页首帧空白；注入 `pages` prop 便于测试。

**约束**（写进组件注释）：key 必须是精确 pathname，不支持动态段；页面内不得用 `useParams`/`useSearch`/`useRouteContext`（依赖 matchContext，常驻渲染时没有，会抛 invariant），读地址用 `useLocation()`。

**覆盖不到**：`/manage/*`——`ManageLayout` 内部还有一层 `<Outlet />`，子页仍随切走重建。要覆盖得缓存整棵子树，另做方案。

**验证**：`keepAliveOutlet.test.tsx` 5 例（首帧只渲染当前页 / 切走不卸载只是隐藏 / 切回 state 不丢 / 非保活路由走 Outlet / 未访问不套容器）；`tsc --noEmit`、biome、`vite build` 全过。注意 `vite build` 会被 safe-delete 守卫拦在 `prepareOutDir`（清 dist/chunks 74 个文件），需 `--outDir /tmp/...` 绕开。
